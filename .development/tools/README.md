# tools

Ruby-скрипты для прямой работы с `.rxdata`. Запускать из **корня проекта**.

---

## rgss_stubs.rb

Библиотека, а не самостоятельный скрипт. Даёт чтение и запись любых `.rxdata`.

```bash
ruby -r./.development/tools/rgss_stubs -e 'ts = load_rxdata("Data/Tilesets.rxdata"); puts ts[1].name'
```

| Функция | Что делает |
|---|---|
| `load_rxdata(path)` | читает `.rxdata`, сам создаёт недостающие классы `RPG::*` |
| `save_rxdata(path, obj)` | пишет через временный файл, делает `.bak`, проверяет читаемость перед подменой |

Проверено: round-trip побайтово идентичен на всех 22 файлах `Data/*.rxdata`.

### Зачем это вообще нужно

`.rxdata` — обычный `Marshal` (версия 4.8), но внутри объекты классов `RPG::*` и `Table`,
которых в системном Ruby нет. Три неочевидные вещи, которые здесь решены:

1. **`const_missing` не работает.** `Marshal` резолвит классы через `rb_path2class`, который
   бросает исключение напрямую и хук не вызывает. Классы создаются реактивно — по имени из
   текста ошибки, с повтором загрузки.
2. **`respond_to_missing?` нельзя делать всеядным.** Если он отвечает `true` на всё,
   `Marshal.dump` решает, что у объекта есть `marshal_dump`, зовёт его через `method_missing`,
   получает `nil` и записывает огрызок вместо данных (99 КБ → 117 байт). Геттер существует
   только если существует сам ivar.
3. **Подклассы встроенных типов.** `PBAnimation < Array` в `PkmnAnimations.rxdata` пишется
   маркером `C:`, и реактивно его не создать — ошибка не содержит имени. Нужен пред-скан
   потока, он реализован в `predefine_user_classes`.

`Table` (тайловые слои карт, passages/priorities/terrain_tags тайлсетов) реализован честно,
с `_load`/`_dump`, потому что это userdef-объект с бинарным payload.

### Полезные примеры

```bash
# что за карта и какой у неё тайлсет
ruby -r./.development/tools/rgss_stubs -e 'm = load_rxdata("Data/Map002.rxdata"); puts "#{m.width}x#{m.height} tileset=#{m.tileset_id}"'

# распределение terrain tags в тайлсете
ruby -r./.development/tools/rgss_stubs -e 't = load_rxdata("Data/Tilesets.rxdata")[1]; h = Hash.new(0); t.terrain_tags.data.each { |v| h[v] += 1 }; p h.sort'

# содержимое скомпилированного кэша плагинов
ruby -r./.development/tools/rgss_stubs -e 'require "zlib"; load_rxdata("Data/PluginScripts.rxdata").each { |p| puts p[0] }'
```

## apply_terrain_tags.rb

Проставляет terrain tag **10** (`:TallGrass`, флаг `deep_bush`) тайлам тайлсета 1.

```bash
# захватить новые пометки тегом 7 и применить
ruby .development/tools/apply_terrain_tags.rb --capture

# просто восстановить теги по сохранённому списку
ruby .development/tools/apply_terrain_tags.rb
```

### Зачем

Редактор RMXP принимает Terrain Tag только **0–7**, а `:TallGrass` имеет номер 10, и все
номера 0–7 заняты стандартными тегами. Поэтому:

- тег **7** используется как **пометка** в редакторе (RMXP её не трогает);
- скрипт переводит помеченные тайлы в настоящий **10**;
- список обработанных ID копится в `data/tall_grass_tiles.txt` и служит источником истины.

Список нужен потому, что RMXP при следующей правке тайлсета сбрасывает непонятное ему
значение 10 обратно в 0 — и без списка информация о том, какие тайлы были высокой травой,
терялась бы навсегда.

### Почему захват отдельным флагом

Тег 7 — это настоящий `:Water` (`can_surf`, `can_fish`). Когда в тайлсете появится настоящая
вода, помеченная семёркой по назначению, автоматический захват превратил бы её в высокую
траву. Поэтому обычный запуск пометки **не трогает** и только предупреждает о них.

### Рабочий порядок

1. Вся правка тайлсета в RMXP — графика, Passage, Bush Flag, пометки тегом 7
2. **Закрыть RMXP** (обязательно, см. `notes/engine-notes.md`)
3. `ruby .development/tools/apply_terrain_tags.rb --capture`
4. Понадобился RMXP снова → после его сохранения теги 10 слетят → закрыть и запустить
   скрипт уже без флага

### Ограничение

Список привязан к **ID тайлов**, а не к картинкам. Вставка рядов в середину
`Graphics/Tilesets/Outside_0.png` сдвинет все ID ниже и сделает список неверным — придётся
захватывать заново. Поэтому ряды дописывать только снизу.
